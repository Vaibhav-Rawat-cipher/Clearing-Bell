# Local integration fixture

From the repository root, run `node scripts/local-dev.mjs` after installing the frontend dependencies and Foundry submodules. The script starts or reuses Anvil on `127.0.0.1:8545`, verifies chain ID 31337, compiles and deploys the contracts, and exports public addresses and ABIs here. The public deployment file is also copied into `frontend/public/deployment.json`.

The script never connects to Hedera, broadcasts to a public network, or reads signing keys. All writes use unlocked local Anvil accounts. A previous local deployment is reused when its engine code still exists. `--reseed` deploys a fresh fixture without deleting chain history. The local node PID is recorded in `anvil.pid`.

Account 0 is the issuer, account 1 an eligible investor, account 2 an eligible seller, account 3 an unverified investor, and account 4 an eligible liquidity provider. Eligible accounts start with 250,000 local USDC and 1,000 local bonds. Round 1 has settled 40 bonds at 99.25 USDC. Round 2 has a 24-hour order window with a buy of 20 at 100 and an ask of 150 at 99.38. The issuer can close early from the issuer console. The primary investor's allowances are reset after seeding so approval interactions can be tested.

This fixture uses mintable test ERC20 tokens and a mutable test identity registry. It exercises the real auction engine and compliance gate, but it is not a deployed Hedera ATS bond or a Uniswap pool. The application submits orders directly to the engine. Public deployment verification must separately validate token transfer restrictions, identity registries, and operator permissions.

The engine accepts visible limit orders with price in settlement base units per bond (6 decimals here) and quantity in bond base units (18 decimals). `closeAndClear` computes price and settles delivery versus payment atomically. For fractional quantities, payments use the difference of cumulative-floor quotes independently on each side. Both sides therefore total the same rounded aggregate amount; an individual fill pays either its floor or ceiling quote. Approval and balance checks must reserve the ceiling of quantity times limit price per buy order. The `Settled` event records quantity and price, while token transfer events record the exact rounded payment.

The engine does not implement sealed orders, commit/reveal, cancellations, escrow, coupon distribution, or document hosting. Balances and approvals must remain sufficient until settlement; an unpayable matched order reverts the entire settlement transaction. The existing hook is not a production swap adapter: its zero delta does not stop a real Uniswap PoolManager from continuing the swap, and its quantity conversion assumes bond units. Its unit tests use a mock PoolManager. Direct engine orders are the supported integration path in this local environment.
